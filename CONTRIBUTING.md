# Contributing to Plant Expression Explorer

Thank you for helping improve Plant Expression Explorer. This project is a
beginner-friendly, descriptive interface for already preprocessed plant
transcriptomics tables. Contributions must preserve its scientific boundaries
and the source data supplied by users.

## Development environment

The acceptance environment uses Python 3.13.9 and the exact package versions in
`requirements.txt`.

```bash
python3.13 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip==26.2.1
python -m pip install -r requirements.txt
```

Run the complete test suite before requesting review:

```bash
.venv/bin/python -m pip check
.venv/bin/python -m pytest
git diff --check
```

## Project structure

- `app.py` and `pages/` contain Streamlit presentation code.
- `plant_expression_explorer/` contains reusable validation, data, analysis,
  and export logic that is independent of Streamlit.
- `tests/` contains pytest regression tests.
- `data/demo/` contains only committed synthetic demonstration data.
- `data/case_studies/` contains app-ready tables derived from public,
  cited datasets. They are written only by a script in `analysis/`, never by
  hand.
- `analysis/` contains offline, reproducible analyses with their own pinned
  `requirements.txt`. This is the only place where models (for example
  DESeq2) are fitted; it is outside the application boundary below.

## Scientific and data-handling boundaries

These boundaries apply to the application (`app.py`, `pages/`,
`plant_expression_explorer/`). Contributions must not imply that the
application:

- processes FASTQ files;
- normalizes or transforms raw counts;
- corrects batch effects;
- fits a differential-expression model;
- establishes statistical significance, condition effects, contrast direction,
  reference levels, regulation, or biological importance; or
- validates experimental design or biological replication.

Do not silently trim, normalize, case-fold, deduplicate, aggregate, impute,
intersect, reorder, discard, or overwrite biological data. Preserve source
values, identifiers, missing values, sample order, DataFrame indices and dtypes,
and the active dataset unless a documented public API explicitly returns a new
derived object.

Descriptive calculations and visualizations must state their assumptions and
limitations. Reusable logic must return controlled, actionable errors for
expected invalid inputs rather than leaking raw exceptions into Streamlit.

## Tests and fixtures

Add or update pytest tests whenever behavior changes. Test normal results,
controlled failures, edge cases, repeated execution, and input non-mutation.
For charts, inspect the rendered specification when order or encoding matters.
For downloads, inspect the generated bytes as well as the source DataFrame.

Never commit private, unpublished, or identifiable biological data. New test
fixtures and demo values must be synthetic, small, deterministic, and clearly
labelled as such. The one exception is a case study under `analysis/` and
`data/case_studies/`: it may use public, published data if the regenerating
script, input URLs with SHA-256 checksums, a citation, and a statement of
limitations are committed alongside it, and the outputs stay small (a few MB).

## Pull-request checklist

- The change stays within the stated application scope.
- User-visible scientific wording is descriptive and does not overclaim.
- Source DataFrames remain unchanged.
- New behavior has regression coverage.
- `.venv/bin/python -m pytest` passes in the pinned environment.
- `python -m pip check` and `git diff --check` pass.
- No credentials, local absolute paths, caches, generated files, or large data
  artifacts are included (case-study outputs written by an `analysis/`
  script are the documented exception; download caches are not).
- README and contributor documentation match the implemented behavior.

## AI-assisted contributions

AI coding assistants are welcome and their use is disclosed in the README.
The same review rules apply: every scientific choice needs a written reason,
every number in a report must be written by code rather than typed, and the
human author must be able to explain and reproduce the change.

Keep commits focused and use a concise imperative subject, for example
`docs: clarify deployment privacy boundaries`.
